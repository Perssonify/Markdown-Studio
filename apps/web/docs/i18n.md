# Interface translation (i18n)

Every string the interface shows — menus, buttons, tooltips, `aria-label`s,
placeholders, toasts, dialog texts, notices, empty states — comes from a
catalog, never from a literal in a component (audit finding A099). English is
the only shipped language today; the layer exists so that a translation is a
catalog file, not a code change across sixty components.

The layer is in `src/i18n/` and is written for this codebase (no library):

| File | What it holds |
|---|---|
| `core.ts` | `t()`, the current language, language selection, plural rules. No React — safe in stores. |
| `react.ts` | `useT()`, `useLocale()`, `t.rich` / `renderRich` for sentences with markup. |
| `en.ts` + `en/<area>.ts` | **The English catalog, the source of truth.** One module per area (`menu`, `toolbar`, `status`, …); every key is prefixed with its area. `MessageKey` is derived from it. |
| `pseudo.ts` | The `en-XA` pseudo-locale transform. |
| `content.ts` | `localizedContent()` for long-form copy (below). |

## Adding a string

1. Put the English text in the module for its area, e.g. `src/i18n/en/toolbar.ts`:

   ```ts
   "toolbar.insertTable": "Insert table",
   ```

   Keys are `<area>.<camelCase>`; reuse an existing key of the same area only
   when the text AND its meaning are the same. `common.*` holds generic button
   verbs (Cancel, Close, Delete, …) — don't use it for anything whose
   translation could depend on context.

2. Use it:

   ```tsx
   // In a component — re-renders when the language changes:
   const t = useT();
   return <Button aria-label={t("toolbar.insertTable")}>{t("toolbar.insertTable")}</Button>;

   // Anywhere else (a callback, a store, a toast) — reads the language at call time:
   import { t } from "../i18n";           // from a store: "../i18n/core" (no React)
   toast.show(t("editor.exportFailed"), "error");
   ```

   A key that is not in the catalog is a type error. In a component, if `t`
   is used inside `useMemo`/`useCallback`/`useEffect`, list it in the
   dependencies: its identity changes exactly when the language does, so a
   memoised label recomputes on a switch.

3. **Values:** `{name}` placeholders, filled from the second argument:
   `"Open {title}"` → `t("graph.openTitle", { title })`. Numbers are inserted
   as `String(n)`; pass a pre-formatted string for anything else.

4. **Counts** are plural messages, chosen by `Intl.PluralRules` from the
   `count` variable:

   ```ts
   "library.documentCount": { one: "{count} document", other: "{count} documents" },
   ```

   `other` is required. `zero`, when present, wins for exactly 0 ("No links").
   Use a plural object for every message that contains a count, even when
   English has one form for all of them (`{ other: "{count} item(s)" }`) — the
   other languages need the forms.

5. **A sentence with markup** is ONE message with tags; `t.rich` supplies the
   elements:

   ```tsx
   // "Stored in <b>this browser</b> only. <link>Learn more</link>"
   t.rich("settings.storedHere", {
     b: (s) => <strong>{s}</strong>,
     link: (s) => <a href="/help#privacy">{s}</a>,
   });
   ```

   A `{name}` part may also be a node (`{ keys: <kbd>⌘K</kbd> }`). Never
   assemble a sentence from several keys: a translator cannot reorder pieces.

6. **Module-level tables** of labels (a menu's item list, a tab list) must be
   read at render, not when the module loads — make the label a getter:

   ```ts
   const TABS = [{ id: "files", get label() { return t("library.tabFiles"); } }];
   ```

**Never translate data**: document titles and folder names (including ones the
app writes, like a new folder's name), ids and values compared in code, storage
keys, URL parameters, `data-*` hooks, file names, export envelopes, and
anything inserted INTO a document (templates, `DEFAULT_CONTENT`, the starter
documents). Key glyphs (`⌘⇧K`) stay in code; developer diagnostics and
`console.*` stay English.

## Long-form copy

The Help page's sections (`src/ui/pages/helpPage/help-content.ts`) and the About page's
prose (`src/ui/pages/aboutPage/about-content.ts`) are content, not labels, and are not in
the catalog. Each exports a map from locale to that locale's version
(`HELP_CONTENT`, `ABOUT_CONTENT`), English required; the page renders
`localizedContent(map)`, which falls back to English. The credits table
(`src/data/credits.ts`) is data. The keyboard-shortcut names
(`src/data/shortcuts.ts`) ARE in the catalog (`shortcuts.*`).

## Adding a language

1. Create `src/i18n/<id>.ts` with the translations:

   ```ts
   import type { MessageKey, Message } from "./core";
   export const de: Partial<Record<MessageKey, Message>> = {
     "common.cancel": "Abbrechen",
     "library.documentCount": { one: "{count} Dokument", other: "{count} Dokumente" },
   };
   ```

   A key it lacks falls back to English, so a catalog can grow gradually.
   Keep every `{placeholder}` and `<tag>` of the English message.

2. Register it in `CATALOGS` in `src/i18n/core.ts` with its autonym and
   writing direction: `de: { id: "de", name: "Deutsch", dir: "ltr", messages: de }`.
   A right-to-left language declares `dir: "rtl"`, and the app shell turns
   `<html>` and its root to `dir="rtl"`.

3. Optionally add the language's Help and About prose to `HELP_CONTENT` /
   `ABOUT_CONTENT`.

The language is chosen from the stored preference `pf:locale`, then
`navigator.language` (exact tag, then base language: `de-AT` finds `de`), then
English. Only languages with a catalog can be chosen. Settings ▸ Appearance
shows a Language picker whenever more than one language is available; `?lang=`
applies one for that page load without saving it (the app shell reads it, like
the other URL parameters).

## The pseudo-locale (`en-XA`)

In development builds (and in the test suite) a second language is always
available: English accented, lengthened by about a third and bracketed —
`[Šávé çĥáñĝéš ····]`. Turn it on with `?lang=en-XA` or Settings ▸ Language.
Then:

- plain English on screen is a string that escaped extraction;
- a label missing its `]` is one that cannot grow and gets clipped;
- `][` inside one phrase is a sentence assembled from pieces.

Placeholders and markup pass through untouched. Production builds cannot select
it (`en-XA` there resolves to English).

## What keeps it this way

- `src/__tests__/i18n-scanner.test.js` parses every client module (`src/ui`,
  `src/editor`, `src/hooks`, `src/formatting`, `src/extensions`,
  `src/integration`, `src/pwa` and the entry shells) and fails on any literal
  with words in JSX text, `aria-label`, `aria-description`, `title`,
  `placeholder`, `alt`, a JSX child expression, a toast message or a dialog
  title/description (including the prompt wrappers and `window.prompt`). Its
  allowlist is explicit, each entry with a reason, and a stale entry fails. It
  cannot see a label in a plain object (`label: "File"`) — the render test
  below does.
- `i18n-catalog.test.js`: every key used exists, no key is unused, every key
  sits in its area's module, placeholders and tags are well-formed and survive
  the pseudo-locale, plural forms agree.
- `i18n-render.test.jsx` mounts the real app under `en-XA` and looks for raw
  English on the menu bar, toolbar, workspace panel, status bar, an open menu
  and the Settings sheet; it also checks `lang`/`dir` for a right-to-left
  catalog.

## `lang` and `dir`

The app shell (`App.tsx`) sets `<html lang dir>` and the shell root's `lang`
/`dir` to the interface language, before paint. The iframe embed is its own
document and does the same for its `<html>`; the library never touches its
host's page. Documents are not assumed to be in the interface
language: every text block carries `dir="auto"` (A099, round 1), and neither the
HTML export nor Print / Save as PDF declares a `lang` — the app does not know
the language a document is written in, and `lang="en"` mislabelled every
non-English document for screen readers, hyphenation and PDF metadata.

## Known gaps

- CodeMirror's accessible name, description and placeholder are set when the
  editor is created; they follow a language switch on the next load (the rich
  pane's follow it live).
- The generated shadcn primitives (`src/components/ui/*`) carry a few
  screen-reader strings ("Close" in the sheet) that are not extracted; they are
  regenerated from upstream, not hand-edited.
- Numbers and dates are formatted as before (`String(n)`, `toLocaleDateString`);
  a translation that needs localised numbers passes them pre-formatted.
- Error messages produced inside workers or by the browser (a regular
  expression's `SyntaxError`) reach the screen as the engine writes them.
